# Windows.UI.Xaml: feasibility scoping

Conclusion: **not feasible as a real implementation in reasonable time, and a "thin subset" would not run real XAML apps.** No XAML code is included. This records why, so the question need not be redone.

## What Wine 11.0 and GE-Proton ship today

- `windows.ui.xaml.dll` in Wine 11.0 has only `ColorHelper` (156 lines) plus stub exports. `include/windows.ui.xaml.idl` declares only `DependencyObject`, `DependencyProperty`, `PropertyMetadata`, `DataTemplateKey` and the change-notification types (256 lines).
- There are no IDLs for `Application`, `Window`, `UIElement`, `FrameworkElement`, `Panel`, `Grid`, `StackPanel`, `TextBlock`, `Button`, `Image`, `ListView`, `Page`, `Frame`, `XamlReader`, the markup interfaces, `Windows.UI.Composition`, or `Windows.UI.Xaml.Media`/`Input`/`Controls`.
- GE-Proton 11-14 adds vkd3d-proton and a few WinRT DLLs (wintypes etc.); it ships no XAML.
- Upstream Wine has no XAML implementation or announced plan for one.

## What even a trivial XAML app needs

1. **Application / hosting.** `Application.Start`, the `Application` activation path, `Window.Current`, `Window.Activate`, `FrameworkView`/`CoreApplicationView` binding the XAML island to our CoreWindow, plus `IFrameworkViewSource`-style activation through `twinapi.appcore`.
2. **Dependency property system.** Property storage, inheritance, change callbacks, attached properties, `Binding`, `VisualStateManager`, a real `DispatcherQueue`-bound threading model.
3. **Layout and controls.** Measure/arrange for Grid, StackPanel, ScrollViewer, plus control templates for Button, TextBox, ListView, etc.
4. **Styles and templates.** The default control templates and `generic.xaml` theme resources live inside the **real Microsoft** `Windows.UI.Xaml.dll` (and `Microsoft.UI.Xaml` / WinUI 2 packages for apps that use them). They can't be redistributed. Writing look-alikes means hand-authoring templates for every control an app touches.
5. **Markup.** Apps ship compiled `.xbf` binary XAML (and `XamlReader.Load` strings). That needs an XBF parser, the `IXamlMetadataProvider` generated by the app's build (type resolution, `Application::LoadComponent`), and the type system behind them.
6. **Rendering and text.** `Windows.UI.Composition` (visual tree, DirectComposition/D2D surfaces), DirectWrite text layout, image decoding, animation/storyboards, plus input, focus and IME routing (`Windows.UI.Text.Core`).
7. **WinUI 2 / `Microsoft.UI.Xaml`.** Many apps depend on a framework package that is itself a large closed-source library on top of system XAML.
8. **IDL work.** Each of the above needs Wine IDL, which doesn't exist; hundreds of interfaces with exact IIDs/vtable order, or apps fail on the first QueryInterface.

## Why a thin subset is not an honest answer

The visible API is small (Page, Grid, StackPanel, TextBlock, Button, Image, ListView). The work underneath is a UI framework: dependency properties, a layout engine, a visual tree, text and image rendering, input routing, and a template/style system. Real apps use the app-generated metadata provider and `.xbf` files and depend on system theme resources, so they would fail at startup (App.xbf load, missing default styles) before reaching any control I implemented. A stub that "starts" and shows a blank window would be misleading. A test app built here would only test the stub against itself, because the only available app (Halo Wars 2) is not XAML and no cross toolchain with the WinRT XAML headers was set up.

Estimated scale for a subset that runs a simple real app: multiple person-months (roughly an implementation-from-scratch of a small UI toolkit with WinRT ABI), versus the hours available in a session.

## If someone wants to pursue it

Smallest credible milestone, in order:
1. Write IDLs for `Application`, `Window`, `UIElement`, `FrameworkElement` and the core controls from the Windows SDK winmd (ReWine/widl-compatible).
2. Implement the dependency-property engine and `Application.Start` over the existing CoreWindow host (`dlls/twinapi.appcore`).
3. Add an XBF parser or only support `XamlReader.Load` text first.
4. Render with D2D/DirectWrite into the CoreWindow swap chain; hand-write default templates.
5. Target one specific open-source XAML UWP app as the test case rather than the whole namespace.

Coordinate with upstream Wine before investing: this overlaps with their `windows.ui.xaml` module.
